# Sparkfeed MCP Server — technical spec

**Status:** draft for review · **Owner:** Sudharsan · **Plane:** PROD-54 · **Last updated:** 2026-08-02

> [!IMPORTANT]
> This is a historical implementation proposal. The current REST and MCP implementation and
> `ROADMAP.md` are authoritative. In particular, Community Edition retains the complete AGPL
> product feature set; Cloud plan restrictions are hosted-service policy, not source-code gates.

This document records the earlier proposal for what an agent could call and what had to exist
underneath those calls.

PROD-54 in Plane is a task with a five-row tool table. This is the spec behind it. Nothing here
is built yet, so everything is still cheap to change. That is the point of reviewing it now.

**Read this first, it is the thesis:**

> The MCP server is not the product boundary. A versioned, API-key-authenticated HTTP API is.
> MCP is a thin client over that API, and so is anything else we ship later (Zapier, a CLI,
> webhooks, a Raycast extension). If we build MCP as a direct database consumer we will fork
> the tenancy, entitlement and pagination logic on day one and pay for it forever.

## Part 1 — What exists today

Verified by reading the repo, not assumed.

### There is no API

Every server operation in the app is a TanStack Start **server function**
(`createServerFn`) in `src/server/rss.ts`. Those are RPC endpoints generated by the framework,
addressed by a build-time hashed id, authenticated by the better-auth **session cookie**, and
not stable across builds. They are not callable by an external client and never will be.

The only real HTTP routes today are:

| Route | Auth | Purpose |
|---|---|---|
| `/api/workspace-data` | session cookie | wraps `getAllData()`, returns the whole workspace |
| `/api/ai` | none beyond demo/flag check | Spark AI chat stream |
| `/api/rss/$slug`, `/api/feed/$slug` | public | outbound XML generation |
| `/api/shared/$folderId` | share token or password | public folder sharing |
| `/api/auth/$` | better-auth | auth surface |

So the answer to *"can the MCP work when nobody has the website open?"* is: **not today, and not
because of the browser.** The browser is irrelevant. The blocker is that there is no
externally-addressable, key-authenticated endpoint for any of it. Building that is the bulk of
this work. MCP itself is the easy part.

### Facts that shape the design

1. **`getAllData()` returns the entire workspace in one response.** All folders, all feeds, all
   scraped feeds, and the 200 most recent articles, joined and sorted in JS
   (`src/server/rss.ts:26-148`). It is exactly the shape MCP must not have.

2. **Article content is only extracted when a human opens the preview panel.**
   `getArticlePreview` (`src/server/rss.ts:327`) fetches the page, runs Readability, and caches
   the result into `articles.content`. Nothing else populates that column. So for any article
   nobody has clicked, `content` is `NULL` and `get_article` will have to fetch and extract on
   demand. That path is already server-side and browser-independent, which is good news: it is
   reusable as-is.

3. **`articles` has no `workspace_id`.** Tenancy is reachable only through
   `articles.feed_id -> feeds.workspace_id`. Every MCP query must carry that join. There is no
   shortcut.

4. **Four mutating server functions do not check tenancy at all.** `toggleBookmark`,
   `toggleReadLater`, `toggleFavorite` and `getArticlePreview` take an id and act on it with no
   workspace filter (`src/server/rss.ts:302-391`). Same for `deleteFeed` and `renameFolder`.
   Today that is latent, because the only caller is a UI that only ever shows you your own ids.
   The moment an agent can pass an arbitrary id with an API key, it is a live IDOR. **This is a
   pre-existing bug that MCP converts into an exploit.** It has to be fixed regardless of MCP,
   and it must be fixed before MCP.

5. **Scraped articles are second-class.** `scraped_articles` has no `content`, no
   `is_favorite`, no `is_read_later`, no `is_bookmarked` columns (`src/db/schema.pg.ts:100`).
   So reader state and cached full text simply do not exist for any site we crawl rather than
   subscribe to. Half the tool surface cannot work on them without a schema change.

6. **`scraped_feeds.site_url` and `scraped_articles.url` are globally `UNIQUE`.** Not unique per
   workspace, globally. If two workspaces add the same site, the second insert collides. This is
   a live multi-tenancy bug that `add_feed` will hit constantly once agents start adding sources
   in bulk.

7. **Article ids live in two disjoint spaces.** `articles.id` and `scraped_articles.id` are
   both bare UUIDs in separate tables. `get_article(id)` is ambiguous without a namespace.

8. **There is no search.** Not a LIKE query, not an index, nothing. Spark AI "search" is
   `ORDER BY published_at DESC LIMIT 20` (`src/server/ai.ts:78`). `search_articles` is a
   from-scratch build, not a wrapper.

9. **Refresh is synchronous and unbounded.** `refreshAllFeeds` runs `Promise.allSettled` over
   every feed in the workspace and awaits the lot (`src/server/rss.ts:250`). No concurrency cap,
   no timeout, no per-host politeness. A workspace with 80 feeds blocks for a minute or more. An
   MCP tool cannot do that.

10. **The cron is two `setInterval` calls in a Nitro plugin** (`src/server/plugins/cron.ts`),
    refreshing *every feed in the database* every 2h. Timers reset on deploy. Two instances do
    everything twice. See PROD-55.

11. **`safeFetch` is not safe** (`src/server/utils/fetch.ts`). It sets a User-Agent, follows
    redirects, and on a TLS failure **retries with certificate verification disabled**. No
    private-range blocking, no DNS pinning, no body cap, no timeout. See PROD-66.

12. **No API keys exist.** No table, no column, no bearer parsing anywhere.

13. **No plans or entitlements exist.** See PROD-62 and PROD-63. MCP is Pro-and-above per
    decision D8, so there is nothing to check against yet.

## Part 2 — Architecture

### The layering

```
  ┌─────────────────────────────────────────────────────────────┐
  │  Claude Desktop / Claude Code / Cursor / any MCP client      │
  └──────────────────┬──────────────────────────┬───────────────┘
                     │ stdio (v1)               │ streamable HTTP (v2)
  ┌──────────────────▼──────────────┐   ┌───────▼──────────────────┐
  │  @sparkfeed/mcp  (npm package)  │   │  /api/mcp  (in-app)      │
  │  local process, no DB access    │   │  remote, hosted          │
  └──────────────────┬──────────────┘   └───────┬──────────────────┘
                     │  HTTPS + Bearer sfk_...  │
  ┌──────────────────▼──────────────────────────▼───────────────┐
  │  src/server/api/v1/*   REST, API-key auth, versioned         │  ← the real boundary
  ├──────────────────────────────────────────────────────────────┤
  │  src/server/services/*   tenancy · entitlements · pagination │  ← shared with the web app
  ├──────────────────────────────────────────────────────────────┤
  │  drizzle · postgres                                          │
  └──────────────────────────────────────────────────────────────┘
```

Both transports import **one** `tools.ts` module that defines the schemas and calls the v1 API.
The stdio package and the remote endpoint differ only in transport and auth handshake.

The web app's server functions get refactored to call the same `services/*` layer, so tenancy
and entitlement checks exist in exactly one place. That refactor is small and it is the thing
that keeps finding #4 above from recurring.

### Why an API layer and not direct DB access from a local stdio server

A stdio server with a Postgres connection string would be less work and would only serve
self-hosters. Cloud users cannot expose their database, so the hosted product would need the
API anyway, and we would end up maintaining two implementations of every filter. One transport
target, one code path, both audiences: the local package points at `http://localhost:3000`,
the cloud user points at `https://app.sparkfeed.dev`. Same package, one env var apart.

### Transport plan

| Phase | Transport | Auth | Who it serves |
|---|---|---|---|
| **v1** | stdio, npm `@sparkfeed/mcp` | `SPARKFEED_API_KEY` env | self-hosters, our own testing, power users |
| **v2** | Streamable HTTP at `/api/mcp` | `Authorization: Bearer sfk_...` | cloud Pro users, one-click install |
| **v3** | Streamable HTTP + OAuth 2.1 | dynamic client registration | directory listings, ChatGPT/Claude connectors |

Per D8, stdio first. It ships without OAuth work and is what our own dogfooding needs.

Client config for v1:

```json
{
  "mcpServers": {
    "sparkfeed": {
      "command": "npx",
      "args": ["-y", "@sparkfeed/mcp"],
      "env": {
        "SPARKFEED_API_KEY": "sfk_live_...",
        "SPARKFEED_URL": "https://app.sparkfeed.dev"
      }
    }
  }
}
```

## Part 3 — The tool catalogue

Tools are grouped by **cost and blast radius**, because that is what determines the guardrail.
Each category gets its own rate-limit bucket, its own scope, and its own entitlement check.

| Category | Reads | Writes | Outbound network | AI spend | Bucket |
|---|---|---|---|---|---|
| 1. Discovery | ✓ | | | | 120/min |
| 2. Retrieval | ✓ | | on cache miss | | 60/min |
| 3. Ingestion | ✓ | ✓ | ✓ | | 10/min |
| 4. Curation | ✓ | ✓ | | | 60/min |
| 5. Synthesis | ✓ | | | ✓ | metered |

### 1. Discovery — cheap, structural, never returns article bodies

**`get_workspace_info()`**

The orientation call. An agent should be able to open with this and know what it is allowed to
do without guessing and getting 403s.

```jsonc
{
  "workspace": { "id": "ws_...", "name": "Acme Research" },
  "plan": "pro",
  "counts": { "folders": 6, "feeds": 84, "articles_30d": 2140 },
  "capabilities": ["feeds:read", "articles:read", "articles:write", "refresh"],
  "limits": { "search_limit_max": 50, "refresh_per_min": 10, "response_bytes_max": 102400 }
}
```

**`list_folders()`**

```jsonc
{ "folders": [
  { "id": "fld_...", "name": "AI Research", "feed_count": 12,
    "unread_count": 47, "latest_article_at": "2026-08-02T09:14:00Z" }
]}
```

No pagination: nobody has 500 folders, and the whole point is that this is one cheap call.
No article bodies, ever.

**`list_feeds({ folder_id?, type?, health?, cursor?, limit? })`**

`type`: `rss` | `scraped`. `health`: `ok` | `failing` | `disabled`.

```jsonc
{ "feeds": [
  { "id": "fed_...", "name": "Simon Willison", "site_url": "https://simonwillison.net/",
    "folder_id": "fld_...", "type": "rss", "last_fetched_at": "2026-08-02T08:00:00Z",
    "consecutive_failures": 0, "article_count_30d": 41 }
], "next_cursor": null }
```

`health` and `consecutive_failures` depend on PROD-55 landing. Until then they are omitted
rather than faked.

### 2. Retrieval — bounded, the workhorses

**`search_articles({ query?, folder_id?, feed_id?, since?, until?, unread_only?, favorites_only?, sort?, limit?, cursor? })`**

One tool, not two. `query` is optional: omit it and you get most-recent-first, which is the
single most common agent request ("what is new in my AI folder this week"). Splitting that into
a separate `list_recent_articles` would give the model two nearly-identical tools to choose
between, and models pick badly when tools overlap.

- `sort`: `relevance` (default when `query` is present) | `newest` (default otherwise)
- `limit`: default **20**, max **50**
- Returns metadata and a **300-character snippet only**. Never full text.

```jsonc
{ "articles": [
  { "id": "art_9f3c...", "title": "Prompt caching, one year on",
    "url": "https://simonwillison.net/2026/Aug/1/prompt-caching/",
    "source": { "feed_id": "fed_...", "name": "Simon Willison" },
    "folder": { "id": "fld_...", "name": "AI Research" },
    "published_at": "2026-08-01T17:22:00Z",
    "snippet": "A year after the first providers shipped prompt caching, the...",
    "is_read": false, "is_favorite": false, "has_full_text": true, "word_count": 2140 }
], "next_cursor": "eyJwIjoiMjAyNi0wOC0wMSIsImkiOiI5ZjNjIn0", "total_estimate": 214 }
```

`has_full_text` tells the agent whether `get_article` will be instant (cached) or slow (live
fetch). Small field, meaningfully better agent behaviour.

**`get_article({ id, format?, max_chars?, offset? })`**

This is the "read the whole blog" path, and it is deliberately **singular**. One article per
call. That single constraint is the entire answer to "never send huge responses": the expensive
operation is opt-in and cannot be batched into a flood.

- `format`: `markdown` (default) | `text` | `html`
- `max_chars`: default **50,000**, hard max **80,000**
- `offset`: for continuing a long article

Resolution order:
1. `articles.content` cache hit, serve it.
2. Cache miss, `safeFetch` the link, run `extractReadable`
   (`src/server/utils/extract.ts`), write the result back to the cache, serve it.
3. Extraction fails, fall back to the RSS `description`, and say so in `source_quality`.

Step 2 is the direct answer to *"the MCP should be able to read that article from our endpoint
even if the app was never opened."* It already works that way server-side; it just needs an
API route in front of it.

```jsonc
{ "id": "art_9f3c...", "title": "...", "url": "...", "author": null,
  "published_at": "2026-08-01T17:22:00Z",
  "content": "# Prompt caching, one year on\n\n...",
  "format": "markdown", "word_count": 2140,
  "truncated": false, "next_offset": null,
  "source_quality": "extracted",       // extracted | rss_description | failed
  "fetched_at": "2026-08-02T09:20:11Z" }
```

Markdown, not HTML, is the default because the consumer is a language model. That needs an
HTML-to-markdown step (`turndown`) on top of the existing Readability output.

**`preview_source({ url })`**

Dry run before committing. Does this URL have a discoverable feed? What do its last few items
look like? Lets an agent evaluate a source without polluting the workspace, which is exactly
what you want before an agent adds forty of them.

Reuses `detectRSSFeed`. Read-only, but network-touching, so it sits in the **ingestion** rate
bucket despite being a retrieval-shaped call.

### 3. Ingestion — side-effecting, slow, hits the open internet

**`refresh({ scope, id?, wait? })`**

`scope`: `feed` | `folder` | `workspace`. This is the tool with a genuine architectural
dependency, so it gets its own section below.

```jsonc
{ "job_id": "job_...", "status": "queued",
  "feeds_queued": 12, "poll_after_ms": 3000 }
```

**`get_refresh_status({ job_id })`**

```jsonc
{ "job_id": "job_...", "status": "completed",
  "feeds_total": 12, "feeds_done": 12,
  "new_articles": 7, "failures": [{ "feed_id": "fed_...", "error": "timeout" }] }
```

**`add_feed({ url, folder_id?, name?, include_keywords?, exclude_keywords? })`**

Reuses `createFeed`'s logic: try RSS autodiscovery, fall back to the scraper. Returns which
path it took, because that determines what the agent can do with it afterwards (scraped feeds
have no reader state, see finding #5).

Blocked by the global-uniqueness bug in finding #6.

### 4. Curation — cheap writes, agent-safe

- **`mark_read({ article_ids, state })`** — up to 100 ids per call
- **`set_favorite({ article_ids, state })`**
- **`set_read_later({ article_ids, state })`**
- **`create_folder({ name })`**
- **`move_feed({ feed_id, folder_id })`**

Batched by id array rather than one call per article, because an agent triaging a morning's
reading will otherwise make sixty round trips.

**Deliberately absent: every destructive tool.** No `delete_feed`, no `delete_folder`, no
`delete_article`, no `remove_member`. An agent misreading an instruction and deleting a folder
of 40 curated sources is unrecoverable, and there is no undo in the product. Deletion stays in
the UI where a human clicks it. This is a product decision, not a technical one, and it is
worth being explicit about.

Read state is **per workspace, not per user** (`articles.is_read` is a single column). In a
shared workspace, an agent marking things read marks them read for everyone. That is existing
product behaviour; MCP inherits it. Flagging it because it will surprise someone.

### 5. Synthesis — expensive, metered

**`get_digest({ scope, id?, since?, style? })`** — server-side summary of what is new.

**Recommendation: cut this from v1.** The client calling us over MCP is already a language
model. Having our server call *another* model to summarize, on our AI credits, so that the
first model can read the summary, is a strange trade. The agent can summarize the snippets
itself for free.

The counter-argument is real but narrow: if an agent wants "what happened across 200 articles
this week," shipping 200 snippets costs it maybe 60KB of context, whereas a server-side digest
costs 500 tokens. That is a genuine win for large-scope questions.

So: ship `search_articles` with good snippets in v1, watch whether agents actually pull large
lists repeatedly, and add `get_digest` in v2 if they do. Building an AI-metered tool before
knowing it is needed means building credit accounting, per-key AI quotas and prompt tuning for
a use case we are guessing at.

### Resources and prompts (v2)

MCP has three primitives and we are only using one. Worth noting now so the v1 shape does not
foreclose them:

- **Resources** — `sparkfeed://folder/{id}`, `sparkfeed://article/{id}`. Lets a user attach a
  folder as context in Claude Desktop with no tool call at all. Cheap to add later.
- **Prompts** — `daily-briefing`, `catch-up-on`, `research-topic`. Pre-written workflows the
  user picks from a menu. This is where most of the perceived product quality will come from,
  and it is almost entirely prompt-writing rather than engineering.

## Part 4 — The refresh problem

The most interesting design question, and the one the current architecture answers badly.

`refreshAllFeeds` awaits every fetch inline. Over MCP that means a tool call that blocks for a
minute and then hits the client's timeout. Three options:

| Option | Cost | Verdict |
|---|---|---|
| **A.** Keep it synchronous, cap the scope | trivial | fine for `scope: feed`, wrong for anything larger |
| **B.** Add a job queue (BullMQ + Redis) | new infrastructure, new failure mode | disproportionate |
| **C.** Set `next_fetch_at = now()` and let the scheduler claim it | needs PROD-55 | **this one** |

**Option C, and it is worth spelling out why:** PROD-55 already plans to give feeds a
`next_fetch_at` column and a worker that claims due rows with
`SELECT ... WHERE next_fetch_at <= now() ORDER BY next_fetch_at LIMIT n FOR UPDATE SKIP LOCKED`.
Once that exists, "refresh" is a single `UPDATE ... SET next_fetch_at = now()` and the worker
picks the rows up within seconds. The claim loop *is* the job queue. `get_refresh_status` is
then just reading `last_fetched_at` and `consecutive_failures` off the rows the job touched.

That makes **PROD-55 a hard dependency of a well-behaved `refresh` tool**, which is not how it
was previously sequenced as post-launch work. It should be ordered
before MCP.

**Interim, if MCP ships first:** allow `scope: "feed"` synchronously with a 15s deadline, and
return `501 not_implemented` for folder and workspace scope with a message saying so. A tool
that honestly refuses is better than one that times out.

**Politeness guardrails, non-negotiable in either version:**

- Per-feed cooldown of **5 minutes**. A second refresh inside the window is a no-op that returns
  `{ status: "skipped", reason: "cooled_down", last_fetched_at }`. Agents poll far harder than
  humans, and our User-Agent is what publishers will block.
- Per-host concurrency of 1, global concurrency cap.
- Conditional requests (`ETag` / `If-Modified-Since`). Most polls become a body-less 304. This
  is the single biggest cost and politeness win available and it is roughly a day of work.

## Part 5 — Cross-cutting guardrails

### Response budget

One serializer enforces a **100KB ceiling** on every response. Nothing else is trusted to be
polite. On overflow the payload is truncated at an item boundary and gains:

```jsonc
{ "truncated": true, "returned": 14, "next_cursor": "...",
  "hint": "Response exceeded 100KB. Call again with the cursor, or narrow with folder_id/since." }
```

The hint is written for a model to act on, not for a log file.

### Pagination

**Keyset, not `OFFSET`.** Cursor is base64 of `{ sort_value, id }`, and the query becomes
`WHERE (published_at, id) < (:v, :id) ORDER BY published_at DESC, id DESC LIMIT :n`. Same effort
as `OFFSET`, correct under concurrent inserts, and stays fast at depth. `LIMIT` goes into SQL,
never into a JS `.slice()` after the fact.

### Identifiers

Prefixed and opaque: `fld_`, `fed_`, `art_`, `scr_`, `job_`, `ws_`. The `art_` / `scr_` split is
what disambiguates the two article tables (finding #7). Prefixes are load-bearing for routing,
not decoration, and ids must never be reused across workspaces.

### Errors

Structured, with a code the client can branch on and a message written to tell the agent what to
do next:

```jsonc
{ "error": { "code": "entitlement_required", "message":
  "MCP access requires a Pro plan. This workspace is on Free.",
  "upgrade_url": "https://sparkfeed.dev/#pricing" } }
```

Codes: `unauthorized`, `forbidden`, `not_found`, `invalid_argument`, `rate_limited`,
`entitlement_required`, `upstream_failed`, `not_implemented`.

### Auth

`api_keys` table:

| Column | Note |
|---|---|
| `id` | `key_...` |
| `workspace_id` | the tenancy anchor, every query filters on it |
| `created_by_user_id` | audit |
| `name` | user-supplied label |
| `hash` | sha256 of the raw key. The raw key is shown once, never stored |
| `prefix` | first 12 chars, for display in settings |
| `scopes` | JSON array |
| `last_used_at`, `expires_at`, `revoked_at`, `created_at` | |

Format `sfk_live_<32 bytes base62>` / `sfk_test_<...>`.

**Open question:** better-auth ships an `apiKey` plugin that does key generation, hashing,
verification and per-key rate limiting, and we already run better-auth with the organization
plugin. Using it would save the whole table and most of the middleware. It needs an evaluation
against our scope model before committing. See D14.

Scopes map to the five categories: `workspace:read`, `articles:read`, `articles:write`,
`feeds:write`, `refresh`, `ai`. Entitlement is re-checked **per call**, not per session, because
a plan can lapse mid-session.

### Search

No search exists at all, so this is a build. Postgres:

```sql
ALTER TABLE articles ADD COLUMN search_vector tsvector
  GENERATED ALWAYS AS (
    setweight(to_tsvector('english', coalesce(title, '')), 'A') ||
    setweight(to_tsvector('english', coalesce(description, '')), 'B')
  ) STORED;
CREATE INDEX articles_search_idx ON articles USING GIN (search_vector);
```

Rank with `ts_rank`. Demo mode runs SQLite, which has no `tsvector`, so it falls back to `LIKE`
behind one interface. Indexing `content` as well is tempting and should wait: it multiplies index
size for a marginal gain when title and description already carry the signal.

### Rate limits

Per key, per category, as in the Part 3 table. `429` carries `retry_after_ms`. The refresh
bucket is the strict one, and additionally subject to the per-feed cooldown, because that limit
protects other people's servers rather than ours.

## Part 6 — What has to be built underneath

Ordered by dependency. Items already tracked in Plane are marked.

| # | Work | Why MCP needs it | Tracked |
|---|---|---|---|
| 1 | Fix the missing tenancy checks on `toggle*` / `getArticlePreview` / `deleteFeed` | finding #4, IDOR the moment keys exist | **new, urgent** |
| 2 | SSRF hardening of `safeFetch` and friends | `refresh`, `add_feed` and `get_article` all fetch attacker-chosen URLs on demand | PROD-66 |
| 3 | Plans and entitlements | MCP is Pro-only per D8 | PROD-62, PROD-63 |
| 4 | `api_keys` + bearer middleware + settings UI to mint and revoke | the auth story | **new** |
| 5 | `services/*` layer extracted from `rss.ts`, shared with the web app | one tenancy implementation, not two | **new** |
| 6 | `/api/v1/*` REST routes + OpenAPI spec | the actual boundary | **new** |
| 7 | Search vector + GIN index | `search_articles` | **new** |
| 8 | Per-feed scheduler with `next_fetch_at` and `SKIP LOCKED` | makes `refresh` a 5ms write instead of a 60s block | PROD-55 |
| 9 | Schema: `content`, `content_fetched_at`, reader-state columns on `scraped_articles` | finding #5, half the tools are broken on scraped sources otherwise | **new** |
| 10 | Schema: drop the global `UNIQUE` on `scraped_feeds.site_url` and `scraped_articles.url`, make it per workspace | finding #6 | **new** |
| 11 | HTML to markdown (`turndown`) on top of `extractReadable` | `get_article` returns markdown | **new** |
| 12 | `@sparkfeed/mcp` stdio package | the deliverable | PROD-54 |
| 13 | `/api/mcp` remote transport | v2 | PROD-54 |

Items 1, 2 and 3 are Gate A work already. **4 through 7 are the real MCP cost**, and they are
what made the earlier "post-launch, depends on primitives Gate A builds anyway" estimate
optimistic: Gate A builds entitlements, but it does not build API keys, a REST layer, a service
layer or search. Those are net-new and they are most of the effort.

## Part 7 — Decisions needed from you

These were the unresolved decisions when this proposal was written. The numbering is historical.

| ID | Question | My recommendation |
|---|---|---|
| **D13** | Is the public REST API a **product** (documented, versioned, on the pricing page) or an **implementation detail** that only MCP consumes? | Product. It is the same work either way, and "MCP and API access" is already on the Pro card. |
| **D14** | Hand-roll `api_keys`, or use better-auth's `apiKey` plugin? | Evaluate the plugin first. We already run better-auth; if its scope model fits, it removes a table and a middleware. |
| **D15** | Ship `get_digest` in v1? | No. The caller is already a model. Revisit with usage data. |
| **D16** | Any destructive tools, ever? | No. Deletion stays in the UI. |
| **D17** | Does MCP write count against a quota, or is it unlimited within Pro? | Rate-limited but unmetered in v1. Metering needs usage data we do not have. |
| **D18** | Self-hosters: MCP unrestricted, or gated the same as cloud? | Unrestricted. AGPL per D10, the code is theirs, and gating it would be theatre. |
| **D19** | Package name and scope: `@sparkfeed/mcp`? Needs the npm org. | Yes, and claim the org early. |
| **D20** | Does `get_article` re-extract when the cache is stale, and after how long? | Serve cache indefinitely, add `?refresh=true`. Articles do not change. |

## Part 8 — Build order

**Milestone 1 — the boundary.** Items 1, 4, 5, 6. API keys, service layer, `/api/v1/folders`,
`/api/v1/feeds`, `/api/v1/articles`, `/api/v1/articles/{id}`. Testable with `curl` alone. This
is the milestone where "works without the website open" becomes true.

**Milestone 2 — retrieval quality.** Items 7, 9, 11. Search index, scraped-article parity,
markdown output. After this, `search_articles` and `get_article` are genuinely good.

**Milestone 3 — the stdio server.** Item 12. Tool schemas, the response-budget serializer,
error mapping, the npm package. Small, once 1 and 2 exist.

**Milestone 4 — refresh.** Items 8 and 2. Scheduler rewrite plus SSRF hardening, then the
`refresh` and `add_feed` tools. Sequenced last because it is the only part with a genuine
infrastructure dependency, and the read-only server is useful without it.

**Milestone 5 — remote.** Item 13, plus OAuth for directory listings.

## Appendix A — What a good session looks like

The design target. An agent answering "what did my AI folder say about prompt caching this
week, and read me the best one" should cost four calls and stay under 30KB:

```
1. list_folders()                                          →  6 folders, 1.2KB
2. search_articles({ query: "prompt caching",
                     folder_id: "fld_ai", since: "7d" })    →  9 hits, 4.1KB of snippets
3. get_article({ id: "art_9f3c" })                          →  1 article, 14KB markdown
4. set_favorite({ article_ids: ["art_9f3c"], state: true }) →  ack, 200 bytes
```

Compare with today's `getAllData()`: one call, the entire workspace, several hundred KB, and no
way to ask a narrower question. That contrast is the whole spec in one line.

## Appendix B — Explicit non-goals for v1

- Workspace, member and invite management
- Billing or subscription tools
- OPML import and export
- Share-link creation
- Webhooks (adjacent, separate spec)
- Writing articles or feeds from outside sources into Sparkfeed
- Anything destructive
